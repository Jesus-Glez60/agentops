---
title: "task sync-linear --push must push before pulling, and only one task's local edit survives per sync call"
type: gotcha
---

Live-tested against a real Linear workspace (a dedicated AgentOps testing project the user set up). Found and fixed a real bug: task_sync_linear (agentops-cli) originally pulled first, then pushed -- but pull_issues's upsert_external_task overwrites the local status field for every synced task, so by the time push read task.status it had already been silently reverted to whatever Linear currently had, making --push a no-op that still reported success. Fixed by pushing before pulling. Confirmed fixed via a real round trip (todo -> in_progress -> done -> back to todo) against 4 real Linear issues, verified by re-pulling after each push. Also added a check on issueUpdate's own success field in the GraphQL response -- Linear can return HTTP 200 with no top-level errors yet still report success: false on the mutation payload, which the original code silently ignored. Separately, a real usability gotcha, not itself a bug: sync-linear --push N's own pull step refreshes ALL local tasks from Linear, not just task N -- so making several local update-status calls across different tasks BEFORE syncing any of them will silently clobber the not-yet-synced ones back to Linear's current state on the very next sync-linear call (confirmed live: batching 3 local edits then pushing them one at a time only the last one's local edit survived, the earlier ones got silently reverted by the middle pushes' own pull step). The intended usage pattern is one local edit immediately followed by one push, not batching several local edits before syncing -- worth remembering for Phase 6's automated dispatch, which must never batch multiple local status changes before syncing them.
