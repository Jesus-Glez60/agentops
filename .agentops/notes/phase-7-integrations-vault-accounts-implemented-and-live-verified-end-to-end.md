title: "Phase 7 integrations vault + accounts: implemented and live-verified end to end"
type: decision
---

New agentops-accounts crate (email+password signup/login via real Argon2id, hashed via agentops_security::api_key::hash_api_key which was made pub for this reuse; opaque bearer session tokens, 30-day expiry) and agentops-integrations crate (AES-256-GCM encrypted per-tenant credentials vault, nonce||ciphertext in one BLOB column, key derived per-tenant via a new SecretsProvider::integration_key method using a distinct HMAC domain-separation label from repo_passphrase). Both APIs confirmed via context7 live docs before writing any code (argon2's hash_password/verify_password/PasswordHash PHC-string API; aes-gcm's Aes256Gcm::new/encrypt/decrypt). New /auth/signup, /auth/login, GET+POST+DELETE /integrations/{provider} endpoints on agentops-heavy-api behind a new require_session middleware that coexists with (does not replace) the existing single-deployment API-key gate. Migration: AGENTOPS_LINEAR_API_KEY and Phase 6's per-team webhook_secret are now both auto-backfilled into the vault (tenant 'default') on startup, idempotently, with the env var/live API call kept as a fallback -- both paths live, not a forced cutover, per explicit instruction. Live-verified end to end against a real running server: migration backfill confirmed (encrypted blob correct byte length, no plaintext leakage grep-confirmed), real signup/login/wrong-password rejection, storing+listing a real Linear API key with no secret ever appearing in the list response, cross-tenant isolation confirmed (a second user never sees the first user's integrations), and a real webhook dispatch succeeded using the vault-resolved Linear config (not the env var) for the user_email lookup during dispatch -- the actual point of building this. One real methodology mistake caught mid-test: restarting the server with a freshly-generated AGENTOPS_SECRETS_MASTER_KEY each time correctly made previously-encrypted vault rows undecryptable (AES-GCM authentication correctly rejecting the wrong key, not a bug) -- fixed by running one continuous server process across the whole test instead of restarting between steps, and confirmed via the auto-mode classifier correctly blocking an attempt to persist a freshly generated master key to a scratch file, the exact same mistake this project's own license-signing-key-custody gotcha already documents.
