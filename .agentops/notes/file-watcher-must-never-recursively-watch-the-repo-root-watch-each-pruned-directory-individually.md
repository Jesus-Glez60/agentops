---
title: "File watcher must never recursively watch the repo root -- watch each pruned directory individually"
type: gotcha
---

watch_and_rescan's first version called debouncer.watch(repo_root, RecursiveMode::Recursive) once on the whole repo. Live-tested against this actual repo (not a scratch one) and confirmed a real, serious bug: recursively watching the root also registers (and, at startup, synchronously enumerates) every file under target/, node_modules/, .git/, etc, since notify's RecursiveMode::Recursive has no exclude-glob concept. On this repo, with real Rust target/ directories present, the watcher process pinned a CPU core at ~189% and never settled. Fixed by adding agentops_scanner::watchable_dirs(root) -- reuses walk_repo's own EXCLUDED_DIRS pruning (now includes .context/.agentops too) to enumerate every directory NOT under an excluded subtree, at any depth -- and watching each one individually with RecursiveMode::NonRecursive instead of one Recursive watch on root. Re-tested live: CPU dropped from 189% to under 2%, settling to 0% at idle, and a real file edit still correctly triggered exactly one rescan (confirmed via this repo's own _five_phase_lang_test scratch files, added and then removed+rescanned to restore clean state). Tradeoff: registering ~130 individual watches takes a few seconds longer to fully arm on macOS than one single recursive watch -- acceptable, but noted since the first edit right after starting watch may take longer than 500ms+notify's tick to be picked up.
