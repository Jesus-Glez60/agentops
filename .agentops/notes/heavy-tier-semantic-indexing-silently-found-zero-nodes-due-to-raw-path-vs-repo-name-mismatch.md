---
title: "heavy-tier semantic indexing silently found zero nodes due to raw-path-vs-repo_name mismatch"
type: gotcha
---

Live-tested agentops-heavy-api's /search/index endpoint against this repo's own real, populated graph.db and got indexed:0 with no error. Root cause: collect_index_items(store, repo) queries GraphStore::nodes_by_kind(repo, kind), which is repo-scoped in this rebuild (unlike main's original, unscoped version) -- but the handler passed the raw request path (e.g. the full filesystem path) as the repo argument, while nodes are actually stored under the canonicalized directory name via agentops_mcp::scan::repo_name() (e.g. just 'agentops'). On main this mismatch was harmless since nodes_by_kind never filtered by repo at all, only used it to tag Qdrant metadata -- it only became a real, silent bug once repo-scoping was correctly added to the query itself. Fixed by adding a repo_name() helper to agentops-heavy-embeddings (mirroring agentops_mcp::scan::repo_name exactly, since that crate isn't reachable from the separate agentops-heavy workspace) and using it at every indexing and search call site in both agentops-heavy-api and agentops-heavy-mcp. Also caught: a completely stale agentops-heavy-api process had been running in the background since July 31 (10+ days), silently listening on the same default port my freshly-built test server tried to bind to -- my new binary died immediately on port conflict, and my first round of 'successful' live tests actually exercised that old process, not my new code. Lesson: always verify a live-test server's own startup log/PID before trusting its responses, not just that curl got a 200.
