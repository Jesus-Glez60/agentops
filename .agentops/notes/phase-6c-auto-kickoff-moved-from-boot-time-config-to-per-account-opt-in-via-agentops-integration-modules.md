---
title: "Phase 6c: auto-kickoff moved from boot-time config to per-account opt-in via agentops-integration-modules"
type: decision
---

Live-testing Phase 6b's new vault-backed test routes surfaced a real architecture gap: POST /integrations/{provider} (Phase 7) always stores a credential under the signed-up user's own randomly-generated tenant (agentops_accounts::AccountStore::signup calls new_random_id, no way to force a specific tenant), but Module 9's webhook/auto-kickoff path was hardcoded to resolve everything against a literal default tenant, set once at server boot from a JSON config file (AGENTOPS_LINEAR_AUTO_KICKOFF_CONFIG). A real user signing up and adding their Linear key the actual designed way would never have it found by the webhook receiver. This became impossible to paper over with an env var once AGENTOPS_LINEAR_API_KEY/AGENTOPS_ANTHROPIC_API_KEY env-var fallbacks were deliberately deprecated earlier the same session (resolve_linear_config/resolve_anthropic_config are vault-only now, no env fallback, no startup migration backfill). The fix, per explicit user direction, went further than patching the one mismatch: generalized into agentops-integration-modules, a new heavy-tier crate and the standard provider-agnostic enrollment mechanism (module_enrollments table: tenant, module_name, opaque JSON config, enabled), deliberately separate from agentops-integrations (which custodies secrets) the same way Phase 7 already split identity from secrets. Linear auto-kickoff is the first consumer, module name linear_auto_kickoff. New session-authenticated routes: POST/GET /linear/auto-kickoff, DELETE /linear/auto-kickoff/{team_id}, all requiring a stored Linear credential first and live-registering the real webhook on enroll. The webhook receiver now loads every enabled enrollment across every tenant per request and resolves each matched tenant's own LinearConfig for dispatch, instead of one shared boot-time config. Live-verified end to end via the real flow: POST /auth/signup, POST /integrations/linear with a real key, POST /linear/auto-kickoff, a real Linear ticket, correct dispatch with the real per-account tenant id in the log line. Along the way this live pass also caught and fixed a real, previously-latent bug in the open-core agentops-graph crate: SqliteGraphStore::delete_nodes deleted from nodes without first removing edges rows referencing the pruned node (edges.src_id/dst_id both REFERENCES nodes(id), no cascade), so pruning any stale node that still had an edge pointing to or from it (the common case, e.g. a removed file's DependsOn edges) failed a foreign-key constraint and aborted the whole scan. agentops-graph-pg already had ON DELETE CASCADE on the matching Postgres FK, so only the SQLite adapter was affected. Fixed by deleting matching edges rows before the nodes delete; regression test added.
