---
title: "SSH deploy-key isolation leaked through the caller's own ~/.ssh/config"
type: gotcha
---

Live-tested agentops-repo-access's connect+verify flow against this repo's own real GitHub remote. Generated a fresh, never-registered deploy key, called verify, and it reported 'active' -- a false positive. The remote URL used a Host alias (github-personal) that has its own IdentityFile entry in the local ~/.ssh/config; ssh still loads that config file alongside the command's own -i/-o IdentitiesOnly=yes flags (IdentitiesOnly only restricts to explicitly configured identities, and the config-file IdentityFile counts as explicitly configured too), so the real, broader-scoped personal key got offered and GitHub authenticated with that instead of the isolated deploy key. This defeats the crate's own stated one-dedicated-keypair-per-repo threat model -- a verify call could report success for a repo the deploy key was never actually granted access to. Fixed by adding -F /dev/null to the ssh invocation, forcing it to ignore any user/system ssh config entirely. Re-tested with the canonical git@github.com URL (no local alias to leak through): the same never-registered key now correctly fails with 'Permission denied (publickey)'. Caught only because live testing used a repo with a real, pre-existing personal SSH config entry -- a synthetic/unreachable-host test (already in the unit suite) could never have surfaced this specific leak.
